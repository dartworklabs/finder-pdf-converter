## Purpose and success

Allow a person using the retained manager to remove **their verified lease-aware managed installation** with an explicit, informed confirmation and a recoverable transaction. **Material scope choice:** the currently deployed non-cooperating installation in the owner’s account cannot be removed or adopted by this first release; the manager must say so clearly, preserve it, and provide manual guidance that does not ask the user to delete an unverified item. The owner can approve this limited removal scope, request further research into support for the current installation, or approve only CI while that research continues; the explicit choices are below. Preserve their files and anything whose ownership or contents cannot be proved. Add truthful GitHub Actions feedback for the checks that can actually run on a hosted Mac, without claiming that it proves the long backend suite or live Finder behavior.

Success means the selected four owned targets are absent after a completed transaction, or the old complete set is restored, or all available preimages and evidence remain with a clear recovery-required result. No outcome presents an uncertain partial state as success. Active conversion, review, merge, and print consumers retain what they need. CI reports the actual checks and fails if a required check did not run.

## Scope and non-scope

In scope: removal of provably lease-aware managed installations only, preparation, exact-target confirmation, mutation, crash recovery, lifecycle exclusion shared with installation, native English/Korean manager integration, safe isolated verification, and a bounded GitHub Actions workflow. Eligible installations are new lease-aware managed installations in a verified clean new account, or installations with a trustworthy record proving they originated and remained lease-aware from the first installation of this version. Unknown histories are unsupported; target absence alone is not proof that no older uncooperative consumer exists. This extends the existing public maintenance protocol and the journal's contract; it does not weaken installation ownership or recovery.

Out of scope: in-place transition or removal of the current non-cooperating managed version; removing a checkout/legacy installation; adopting or deleting an unverified installation; deleting the retained manager app, support root, arbitrary retained preparations, prior recovery backups, preferences, user documents, PDFs, printers or system settings; login-service changes without an explicit selection; public distribution/signing; physical printing; changing conversion semantics; changing branch protection or deleting or moving an existing required check. After successful removal, explain that the retained app can be deleted manually if the owner chooses; the optional menu remains separate and the optional login service changes only if selected. Accurately show any remaining state. No QA updates or removes the owner’s working installation. Do not call app deletion a completed part of removal.

## 설계 이유와 제약

- **role / path: ownership / `installer/managed-engine.js`, `installer/README.md`.** The existing managed proof binds the full source and installed workflows; neither a filename nor the present 37-file count grants authority to delete future or unknown contents.
- **role / path: transaction / `installer/README.md`.** Four renames are not one filesystem-atomic operation. Recovery retains evidence when identity or content cannot be proved; the existing install journal cannot simply treat absence as an install postimage.
- **role / path: runtime / `conversion-session.sh`, `print-fit.sh`.** Consumers may continue after conversion has finished. A process-name scan cannot close the start-versus-removal race, and the existing advisory install lock alone provides no runtime exclusion.
- **role / path: verification / `installer/README.md`.** Temporary `HOME` isolates filesystem paths but not macOS preferences, TCC, Finder registration or ServiceManagement. A hosted runner cannot stand in for a real user's Finder, printer, or login session.

## 충돌·미확인

- **role / path: runtime transition / three installed workflow entry points.** Existing deployed versions do not hold the proposed runtime lease. A clean, enforceable quiescence boundary for the first upgrade from an uncooperative version is not yet established. Do not claim a process scan proves it. Until a safe transition is proved, refuse a mutation whose safety depends on that proof and report the limitation; do not present it as protected. This first release excludes that transition and must clearly disclose that exclusion.
- **role / path: recovery / `installer/managed-engine.js`.** A distinct versioned removal journal and compatibility with interrupted existing install journals must be defined and tested; invalid or unknown versions fail closed. Earlier orphaned or retained preparation/backup directories remain untouched by default.
- **role / path: hosted verification / `.github/workflows/` (proposed).** GitHub's [runner image inventory](https://github.com/actions/runner-images) lists `macos-15` arm64 and `macos-26` labels; labels and images change. Verify availability, SDK/Xcode, native APIs and actual execution in the target repository at implementation time. macOS 26 is a CI environment, not a newly established product minimum.
- **role / path: Finder registration / `installer/README.md`.** Verify what refresh/unregistration can be observed without broad preference or system modifications. If the filesystem transaction succeeds but the Finder menu is stale or refresh fails, report the distinction and corrective guidance; never call rollback or registration success without evidence.

## Proposed contract and data flow

### Authority and preparation

The principal is the current local user. The assets are exactly the managed `~/Library/Application Support/Finder PDF Converter/source` and the three installed `~/Library/Services/{PDF로 변환,용지에 맞춰 인쇄,PDF 합치기}.workflow` bundles. Caller-supplied payload paths, on-disk files, links, journal and confirmation data are untrusted. One backend boundary owns inspection, decisions, mutation and recovery; the UI does not turn a name or path into deletion authority.

Keep existing `inspect`, `install`, and `recover` behavior and closed JSON/exit-code distinctions. Add explicit prepare and execute operations to that same boundary, and extend recovery for a separately identified removal journal. Freeze exact argument names, JSON schema versions, closed reason codes and exit codes in the post-approval plan, preserving old callers. A prepare response is read-only and produces a bounded, short-lived, single-use opaque proposal tied to current user, exact four canonical owned targets, complete verified snapshots protocol version, the explicit login option, and the chosen treatment of this transaction’s staged preimages. It cannot name arbitrary targets or authorize other backups. Store only the minimum needed, with protected ownership and permissions; do not put private paths into ordinary JSON or logs. Reject malformed, expired, replayed, cross-user, changed or unknown proposals. Confirmation of the displayed proposal authorizes exactly that effect, not future removal or cleanup.

Preparation first establishes an eligible lease-aware generation and a proved transition history; it reports the current non-cooperating installation as unsupported, before granting a removal proposal or modifying it. The manager explains this limitation and does not offer a destructive confirmation for that state. Preparation verifies all four as one managed set, including source/receipt, full current inventories, helper signatures, owner identity, content, types, metadata and path ancestry. Reject absent, foreign, altered, extra, symlinked or hard-linked members and uncertain ownership, including races in parent directories. A fully absent installation may be reported as already absent by inspection; a partial set is conflict, not removable by guessing. Do not recursively delete unknown directory contents. Do not execute untrusted old-source scripts. The normal 37-file payload is an observed snapshot only; future payloads must be authorized from their own complete verified inventory.

The manager shows the three named actions and managed source as the exact removal targets, plus what remains: documents/PDFs, retained manager, menu, support root and prior backups. Its dedicated destructive confirmation defaults to Cancel; only the explicit Remove confirmation submits the same proposal. It offers two independent choices:

- **Turn off login launch:** unchecked by default. When selected, query authoritative ServiceManagement state and, if registered, request unregistration and verify the resulting state before moving any of the four filesystem targets. An unavailable, unknown, failed or unverified result stops removal before those moves and reports actual observed state. When unchecked, do not change login launch. If unregistration succeeds but a later filesystem step fails, report that login launch may remain off; do not silently re-enable it. The retained manager and optional menu are not removed.
- **Removal backup:** choose **Preserve by default** or explicitly **Clean up only verified material from this removal**. The second choice permits irreversible cleanup only of this transaction’s verified staged preimages after commit. Existing retained preparations and prior recovery backups are never eligible. Clearing old backups is not implemented in this scope and requires a separate owner decision and approval.

The proposal and confirmation bind both choices to the exact four-target snapshot; changing either requires a new proposal/confirmation. Cancel performs neither ServiceManagement nor filesystem changes. Disable repeated actions and close/quit during a mutation as with installation; busy/conflict/recovery-required remain actionable and honest. Preserve native layout and localized English/Korean copy; no changes to conversion results or unsolicited prompts.

### Runtime admission gate, leases and old-version boundary

macOS `lockf` provides exclusive descriptor locks, not a shared-reader option. Three candidates were considered: (1) a single exclusive lock for every operation, which serializes independent Finder jobs and can hold the whole manager busy through a result window; (2) **a stable admission gate plus individual OS-locked runtime leases**, recommended because it admits concurrent readers while excluding maintenance; and (3) process scanning or PID files, rejected because they cannot close the start race or prove lifetime. This is a proposed protocol, not a claim that it already works.

The admission gate and lease directory are stable, verified per-user objects outside the four replaceable targets. Before any replaceable-resource access, each supported runtime entry acquires the exclusive admission gate, creates a uniquely named, safely opened lease object inside the verified directory, acquires and retains its exclusive OS descriptor lock, then releases the admission gate. It holds that lease until every owned conversion, retry, review, merge and print consumer closes. Lock/descriptor inheritance, launcher failure, signal handling and any child handoff must preserve lifetime; a premature owner exit cannot release protection while a consumer still needs resources. Multiple runtime leases may coexist.

Install, recover and remove hold the admission gate from before examining leases through all mutation, verification and required registration. Under the gate, an active or unverifiable lease makes maintenance return busy/conflict without effects. A stale lease may be handled only after obtaining its OS lock and revalidating its identity and the directory; unknown or substituted entries are retained and block the operation. New runtime admissions cannot race the check or four renames. A process crash releases its OS locks; no PID scan or stale PID alone grants authority. If reliable admission, lease lifetime, safe enumeration or stale-entry handling cannot be implemented and demonstrated on the supported OS, stop instead of asserting exclusion.

The protected set must include all supported entry points that use these resources, including documented direct entry points, or those entry points must refuse unsafe access during mutation. Cooperating new versions cannot protect running or newly starting old versions. This first release supports a new lease-aware installation only with a verified clean new account, or a trustworthy protected installation record and independently verified evidence that all supported installations in that account originated with this lease-aware generation and no prior non-cooperating job can remain or start. A uniquely owned isolated test account or home can establish the conditions for its own fixtures; an arbitrary temporary HOME alone does not establish the real account’s history. Absent target paths alone do not prove that an old process has stopped. A verified clean boot after safe lease adoption may establish that earlier consumers no longer remain, but it cannot prove that the initial replacement of an old installation was safe. If the history or no-old-owner condition cannot be proved, return unsupported-transition/conflict before any live mutation. This explicitly includes the currently installed old generation, not only unknown versions. No restart, logout or removal of the user's working installation is performed for this work.

An in-place barrier for a future change would first need to prove a more difficult contract. In the current code `print-fit.sh` starts both `conversion-session.sh` and `convert.sh` at canonical paths, and `conversion-session.sh` starts `convert.sh`; installing guards at those paths then holding the gate while waiting for old parents can deadlock, while denying nested calls can disrupt an active job. Moreover, `conversion-session.sh` cleanup waits at most ten seconds for its monitor before retaining the session and exiting, so shell-parent disappearance does not prove every consumer is gone. Both scripts derive `script_dir` from `$0`, so moving an original script and naively forwarding to that new path changes resource resolution. A feasible later design must demonstrate race-free guarded admission, continuation of old nested calls without deadlock, complete consumer and orphan detection, faithful canonical-path semantics, bounded recovery and crash handling, all without stopping a user's job. Process inspection alone or a reboot after an unsafe update is not this proof. The future mechanism is not authorized by this spec.

### Transaction, failure and recovery

After confirmation, acquire the admission gate and establish that no runtime lease is active, consume the proposal exactly once, and revalidate the four complete snapshots and parent identities under that boundary. If the user selected login unregistration, obtain and verify the authoritative result now, before moving any target; failure or uncertainty stops without filesystem removal. Revalidate the target snapshots again immediately before any movement. Where a path is acted on, enforce identity at the filesystem operation rather than trusting a previously checked string; reject substitution, links, hard links, path escape and unexpected members. Use a bounded private transaction location, restrictive permissions and same-volume rename preconditions; if those cannot be proved, stop before the first move. Never follow links or recursively remove an unknown tree.

Durably record a versioned removal journal with transaction identity, proposal binding, four original states and each move before/after its effect, including enough information to resolve a crash at each boundary. Move only verified objects to durable staging, not straight to irreversible deletion. After all four are absent and the state is verified, durably mark commit. With the default Preserve choice, keep this transaction’s verified preimages in a bounded durable location and report their retention; lack of safe retention capacity stops before moving targets rather than silently deleting old backups. With the explicit cleanup choice, only after commit delete individually enumerated, revalidated owned staged members from this transaction. Finalization must not delete newly added or changed items. On any ambiguity, preserve the item and all available preimages and journal; return recovery-required with next steps. Validate durability ordering and actual filesystem behavior, including crashes between a rename and its journal update; do not assert four-way atomicity.

Before commit, failure or interruption restores all verified preimages without overwriting anything newly created. A conflict during restoration retains the staged preimages and reports recovery-required. After commit, recovery idempotently honors the confirmed Preserve or cleanup choice; it performs only verified cleanup when that choice authorized it; repeated recovery cannot replay confirmation, overwrite a new installation, or delete unverified data. Opening the manager or invoking another mutation first detects and resolves or safely blocks on the appropriate install or removal journal. An unrecognized, malformed, substituted or incompatible journal never authorizes deletion. Existing retained preparations and old recovery backups are outside this transaction and stay in place. Finder refresh, if available, occurs after verified filesystem commit; failure has a distinct truthful result and is not equivalent to an unchanged installation.

## GitHub Actions proposal

Use a `ubuntu-24.04` portable job and a `macos-15` arm64 native job, with real native build/API checks; record OS, architecture, Xcode/SDK, commands and result. Use `pull_request` and explicit `workflow_dispatch`; do not add an unrestricted branch `push` run of the same checks/tree. The initial PR can exercise its workflow via `pull_request` (a deliberate rerun of that existing PR run can classify a failure); `workflow_dispatch` is available only after the workflow exists on the default branch, so do not claim its first actual run before that happens or merge merely to manufacture evidence. A PR merge-ref and a branch-head tree may differ; report the tested SHA and tree rather than assuming equivalence. Pin external actions to reviewed full commit SHAs, grant only `contents: read`, set checkout `persist-credentials: false`, use no `pull_request_target`, and do not expose secrets or privileged events to fork PR code. No release, package publication, elevated permissions or branch-protection change is authorized.
