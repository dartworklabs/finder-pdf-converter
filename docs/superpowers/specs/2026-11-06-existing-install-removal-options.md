# Existing installation removal: design options

Status: research for a later decision, not an approved removal specification or implementation plan. Scope is the managed installation represented by repository baseline `2730fb4`; other deployed versions must be identified and verified before they can be included. CI work is separate. No removal, settings change, or prototype is authorized by this document.

## Facts and limits

- The three installed actions use the conversion workflow's fixed Resources path in the user's Services directory. A running print or conversion session may open scripts and the review or print app at that path later, including after nested preparation. Input PDF snapshots in `print-fit.sh` are not a full runtime snapshot.
- The old entry points do not participate in an uninstall admission protocol. The conversion session can leave its monitor alive after the parent exits. A process listing, a parent PID, a timeout, disabling a Finder menu, or refreshing registration does not prove that every existing or queued consumer is finished.
- Apple documents choosing which Quick Actions appear in Finder ([Apple Support](https://support.apple.com/en-au/guide/automator/aut73234890a/2.10/mac/15.0)). This is a user-interface availability setting, not documented evidence that already queued actions or other invocation paths have drained. Fast user switching can leave multiple accounts logged in ([Apple Support](https://support.apple.com/en-gu/guide/mac-help/mchlp2439/mac)); switching accounts alone is not logging out.
- Ownership proof currently binds all three workflow links to the owner; validates source and installed resources, generated app source hashes, full inventories and signatures; and checks the managed receipt and helper markers. `installer/managed-engine.js` is the public classification and recovery authority. Changing old scripts in place breaks those checks and does not protect old running code. Historical legacy checkout classification is distinct; it is not proof that every old variant is supported for removal.

## Option 1: user-mediated maintenance window

The user stops initiating conversions, printing and merging, closes or completes their visible tasks, and may hide the three actions through macOS settings. After clearly explaining that hidden or closed does not prove no queued or background work remains, the manager presents the exact verified targets and requests explicit acceptance of that residual interruption risk for this removal. Only then may it perform a transactional removal. The user agrees to refrain from new use throughout the operation; any uncertainty or conflicting evidence stops it. Existing originals and generated PDFs remain outside the target set.

This is practical for the current account and current known managed layout, but it is **best effort**, not a claim that active or queued work cannot be interrupted. The approval is specific to the shown target snapshot and risk, not permission to bypass ownership, recovery or file-change checks. It cannot substitute for a product requirement that promises zero interruption. A manager should report the actual removal, any unconfirmed Finder registration or login-service outcome, and retained recovery material separately. This option needs a new approved spec and rendered before/after PoC before implementation or product integration.

## Option 2: account-offline maintenance research

Explore removal while the target account is actually logged out and prevented from starting work, performed by an independently authorized maintenance environment. This is a candidate for a stronger boundary, not a proven guarantee: establish how target processes, queued LaunchServices requests, other users, login agents and home access behave, and prove admission remains blocked for the entire transaction. Verify identity and permissions without broadening authority or using an untrusted request-supplied home. Fast user switching is insufficient. The current manager operates in the logged-in account, so this would be a separate architecture and authorization decision; no logout, restart, sudo, or external account access is approved here. If an enforceable boundary cannot be established, do not label this zero-interruption removal.

## Option 3: future cooperative runtime

A future installation could admit each top-level job under an installation-generation protocol and, before work begins, produce a verified private runtime containing every script, adapter and both signed native apps. Nested calls would use that same job capability and runtime. Removal would close admission and drain or retain each generation until all consumers, including queued launches and native apps that outlive their parent, are accounted for. Partial startup, copy failure, crash, stale state, app identity, permissions, recovery and cleanup require explicit tests and fail-closed outcomes. Retaining a runtime indefinitely when termination cannot be proved is safer than deleting it prematurely.

This does not retrofit jobs already running or queued under the old generation. A verified migration from the existing installation still needs Option 1's explicit residual-risk acceptance or a separately proven quiescence boundary such as the researched Option 2. New runtime layout, payload identity, signatures, receipt and doctor/ownership rules must evolve together through the normal verified installation transaction; patching installed scripts is not equivalent.

## Common transaction and acceptance criteria for a later specification

1. Inspect and show the actual managed source and all three exact workflow targets, their classification and any recovery state. Only verified managed installations are candidates; foreign, modified, incomplete, unknown variants and pending recovery stop with no removal. Specify legacy support separately; do not infer it from the managed contract.
2. Bind consent to the full inspected snapshot and chosen effects. Acquire the shared installation lock, re-inspect under lock, revalidate before each effect and reject changes. A lock that only installers use is not a job-drain mechanism.
3. Define a versioned removal journal and fixed targets, durable before/after records, checked staged preimages, collision-safe restoration and idempotent retry. Preserve uncertain files, backups and journals on conflicts or faults. Do not assume multiple Trash operations are atomic or always reversible; document the commit and cleanup boundary and verify same-volume assumptions.
4. Treat disabling login launch via the observed `SMAppService` state, optional menu preference, Finder registration and removal of managed files as separate effects and results. Do not kill or delete the running manager; retained app removal is a separate manual action. Never silently report failed or unknown OS state as success.
5. Validate the actual public path using an isolated account and fixture, including queued starts and monitor lifetime, not the real working installation. Test approved snapshot changes, unknown items, active and nested jobs, concurrent maintenance, every journal/move/commit fault, repeated recovery, restored and conflicting cases, OS registration failures and source/PDF preservation. A GUI test that only overrides `HOME` is insufficient: current `installer/ui.js` derives the real user's home for its backend.

No option above has yet established full safety for pre-existing queued work. Option 1 is the bounded user-mediated choice if that residual risk is expressly acceptable; Option 2 requires independent evidence; Option 3 addresses a new generation but does not resolve old jobs by itself.
